# Disaster recovery (2026-09-24)

This review walks ten ways Niyyah could go wrong. For each it gives what detects it, what to do in the first hour, how to recover, how much data can be lost, what members experience, and what stops it happening again. It then separates the procedures that must be **tested** from the ones it is enough to write down, and records the drills that were actually run.

**The product's strongest recovery property is that it is local-first.** A member's answers, map, read, eleven and guide threads live on her phone. The server holds copies she chose to send, plus counts. Most disasters here cost the founder visibility and cost members a server feature for a while. They do not cost members their own work.

The review's worst finding was a backup that could not be restored. That is now fixed and tested on every PR.

## What the review found, and what was fixed

| Found | Now |
|---|---|
| `/export` had no restore path. `docs/INTEGRITY.md` said so; nothing had ever been put back. | `netlify/shared/restore.ts` and `scripts/restore.ts`. A round trip (export, lose, restore, export, equal) runs on every PR. |
| One corrupt record made the whole backup a 503. | Each record is read on its own. The backup carries `skipped: n`, and each skip counts as `fail.export`. |
| With the map lost server-side, the family's vouch ask failed for ever. | `askFamily()` keeps the map again from the phone and retries once, as the door join already did. |
| A wiped store was invisible until someone wrote in. | `/health` records each store's size daily. The `data` check turns red on a loss. |
| A deploy was checked for *landing*, never for *working*. No rollback procedure was written down. | `deployed.yml` smoke-tests the page, the functions and storage, and names the rollback. `docs/DEPLOY.md` has "Rolling back". |
| Old record shapes were never read by the current code. | A golden corpus, `tests/fixtures/records/v0.json` and `v1.json`, is read by every reader on every PR. |
| The sample guide page hard-coded the domain. | It uses the configured host. The domain drill checks it. |

## The ten scenarios

### 1. Netlify outage (site, functions and storage all down)

**Detection**
- The health run (`watch.yml`, every 3 hours) fails when the page does not answer.
- status.netlify.com.
- Members write in, to a mailbox that does not depend on Netlify.

**Immediate response**
- Confirm it on status.netlify.com. There is nothing to operate: it is Netlify's to fix.
- If it runs past a few hours, post once where members gather (the WhatsApp or community channel the founder uses) to say their answers are safe on their phones.
- Do not change anything in the repository or in DNS in a hurry.

**Recovery**
- Automatic when Netlify recovers.
- A Forget me made during the outage finishes on its own the next time the app opens (the pending-forget path).
- A keep or a door join is retried by the member's next tap. Their idempotency keys make the retry the same operation, never a second map.

**Data-loss bound:** none. The integrity work means nothing is half-written.

**User impact**
- A phone that has opened Niyyah before has the app shell cached, so it keeps working offline:
  - the read, Before you say yes on one phone, the map and the offline guide all work;
  - keeping, the door, the vouch, the two-phone eleven and reports each say *that is us, not you* and lose nothing.
- A first-time visitor sees nothing until Netlify returns.

**Prevention:** none possible within one vendor. The standing mitigation is local-first, and `docs/CONTROL.md` ranks the move-off path. The drill: `tests/journeys/netlify-down.test.tsx`.

### 2. Blob data corruption (a record that is not valid JSON, or has the wrong shape)

**Detection**
- `/health` `functions` counts `fail.<route>` when a read throws.
- The weekly sweep's error count turns `sweep` amber.
- `/export`'s `skipped` count.

**Immediate response**
- The route and day are in `/health`. The log line names the key: Netlify → Functions → the route → `[niyyah] <route>:`.
- Read the key with `netlify blobs:get <store> <key>`.

**Recovery**
- A corrupt **map**: the member's phone holds the whole map. Delete the bad key (`netlify blobs:delete maps <code>`). Her next keep answers 404 and re-mints a new code from her phone.
- A corrupt **progress** record: restore that one record from the last backup (`scripts/restore.ts`; it writes only records that are absent), after deleting the bad key.
- Anything else: delete it. The record is regenerated by the member's next action, or lapses.

**Data-loss bound:** that one record, or nothing (a map comes back from the phone; progress comes back as of the last backup).

**User impact**
- The owner of the record sees *that is us, not you* on the affected action until it is fixed.
- Nobody else is affected: every reader skips or isolates the bad record.

**Prevention**
- Every write is `setJSON` from code; nothing writes raw text.
- Readers tolerate old shapes.
- The drills plant non-JSON, strings, arrays, `null` and wrong shapes in every store. No route may crash, the sweep must go on, and the backup must still arrive.

### 3. A lost environment variable

**Detection**

| Variable lost | What shows it |
|---|---|
| `FOUNDER_KEY` | Every health run fails with *"/health answered 401"* |
| `ANTHROPIC_API_KEY` | `claude` goes amber (`not_configured`) |
| A cap variable | Nothing breaks; the cap falls back to its default |
| `VITE_*` | Only after the next build, which uses the defaults (`docs/DEPLOY.md` table) |

**Immediate response**
- Set it again in Netlify → Site configuration → Environment variables, then **redeploy**. Functions read the variables at deploy time.
- `FOUNDER_KEY` also lives as a GitHub secret. Set both, with the same value, in the same hour.

**Recovery:** the next deploy. Nothing was stored differently while the variable was missing.

**Data-loss bound:** none.

**User impact**
- `FOUNDER_KEY`: none; only the founder is locked out.
- `ANTHROPIC_API_KEY`: the guide answers in its offline voice.
- `VITE_SITE_HOST` or `VITE_CONTACT_EMAIL`: the next build falls back to `joinniyyah.com` and `salaam@joinniyyah.com`.

**Prevention**
- The values are kept outside Netlify, in the founder's password manager. On the free plan every variable is plaintext to the team, so the password manager is the record.
- The drills: each secret unset, with its failure shown to be closed or offline, never open.

### 4. A compromised Anthropic key

**Detection**
- `cost` goes red above `OPS_COST_ALERT_USD` (default $20 a day), or amber at 3× the week's average.
- `limits` goes red on `cap.guide-d`.
- An Anthropic usage email.
- A revoked key shows as `claude` red (`auth`) on the next call.

**Immediate response, in this order:**
1. console.anthropic.com → API keys → **delete** the key. Spending stops at once.
2. Create a new key.
3. Set it as `ANTHROPIC_API_KEY` in Netlify and redeploy. Until then the guide is offline, which is safe.
4. Set `GUIDE_DAILY_CAP` lower if the traffic itself is hostile.
5. Rotate `FOUNDER_KEY` too, if the leak was the Netlify team: every variable is plaintext to the team.

**Recovery:** the new key after the redeploy. The spend already made is recoverable only by asking Anthropic.

**Data-loss bound:** none. Money only, bounded by `GUIDE_DAILY_CAP` × about 9¢ a call (about $36 a day), and by the console's monthly spend limit if one is set.

**User impact:** the guide is offline for the minutes between deleting the old key and redeploying with the new one.

**Prevention**
- The console's monthly spend limit, which is **unset** (`docs/CONTROL.md`); only the founder can set it.
- A separate key, with its own limit, for `guide-eval.yml`.
- Quarterly rotation (`docs/CONTROL.md`).

### 5. A bad production deploy

**Detection**
- `deployed.yml` goes red if the commit never goes live, or if it is live but the page, the functions or storage fail the smoke test.
- `client` goes amber when phones report crashes (`chunk` is a screen that never arrived).
- `functions` goes red.

**Immediate response: roll back first, investigate second.** Netlify → Deploys → the last deploy marked Published and green → **Publish deploy**. Then **Stop auto publishing**, so the next push does not re-deploy the bad commit before it is fixed. `docs/DEPLOY.md` "Rolling back" has the steps.

**Recovery**
- Fix on a branch, and let `npm run verify` and the preview pass.
- Merge, **Start auto publishing**, and confirm `deployed.yml` is green.

**Data-loss bound**
- None from the rollback itself: stored records are read-tolerant both ways. An older deploy reading newer records is drilled by the golden corpus.
- A deploy that *wrote* wrongly: records written between the deploy and the rollback may need a targeted repair. The ops counts say when the failures began.

**User impact:** as long as the deploy was live, which is minutes with the smoke test.

**Prevention**
- `npm run verify` gates every build.
- The rendered journeys and the screen audit catch a broken screen before merge.
- The post-deploy smoke test.

### 6. Deleted data (a store, or part of one, gone)

**Detection:** `/health` `data` goes red when a store loses more than 25% of itself since the last day on record (from at least 8 records), or when the safety queue loses reports (from at least 2).

**Immediate response**
1. Stop: do not run the sweep or `/pool?sweep=1`.
2. Take a backup now (`/export`) of what remains.
3. Find out how it happened (the Netlify audit log, and who has team access) before restoring. A deletion that happens again will delete the restore.

**Recovery, by store:**

| Store | Recovery | Loss bound |
|---|---|---|
| `maps` | Nothing to restore: each phone re-keeps its whole map on its next keep, door join or vouch ask, under a new code (drilled). | None of her map. Her vouch, door place and contact under the old code are lost and must be given again. |
| `progress`, `tallies` | `npx tsx scripts/restore.ts backup.json --site <id>` as a dry run, then `--write`. It writes only records that are absent, so members who came back since are kept. | Since the last backup: at most 35 days, or up to 31 before the backup check warns. |
| `cohort` | Rebuilt as members join again. The backup's door counts say how many to expect. | Every door place, until re-joined. |
| `contacts` | From the manual `reach-<date>` backup (`docs/OPERATING.md`). | Since that backup. |
| `vouches`, `couples` | Not backed up, by design (`docs/PRIVACY.md`). A family vouches again; a pair sends the eleven again. | All of them. |
| `reports` | Not backed up. **This is the one loss that matters beyond data**: a concern about a real person. The `data` check exists largely for this. | All open reports. The mitigation is to know the same day and ask members, in the channel, to report again. |
| `ops`, `limits` | Regenerate on their own. | Operational history only. |

**User impact:** the maps case is invisible apart from a new code on the keep card. The vouch and door cases are visible, and she is asked to act again.

**Prevention**
- Netlify team access kept to the founder.
- The `data` check.
- A monthly backup: automatic once the repository is private and `BACKUP_TO_ARTIFACT=true`, and by hand until then.
- The drills: `maps` wiped then recovered by phones; `progress` and `tallies` wiped then restored and compared.

### 7. A broken migration (a change that cannot read what is already stored)

**Detection:**
- **Before merge:** `tests/recovery.test.ts` reads every record shape ever written (`tests/fixtures/records/`) through every reader.
- **After:** `functions` red on the routes that read the old shape.

**Immediate response:** roll back (scenario 5). Reading is the only thing a migration here changes; nothing rewrites records in bulk.

**Recovery:** fix the reader to tolerate the old shape. `docs/INTEGRITY.md` "Schema evolution": add a field and default it on read; change a meaning, then bump `v` and branch on it.

**Data-loss bound:** none. Records are rewritten one by one on their next write, never migrated in bulk, so nothing is lost to a bad migration.

**User impact:** errors on the affected routes until the rollback.

**Prevention:** the golden corpus. A new record shape is added to it by the change that introduces it. Regenerate `v1.json` with the note in the test, and never edit `v0.json`.

### 8. Domain failure (joinniyyah.com lapses, is hijacked, or DNS breaks)

**Detection**
- The health run: the page does not answer.
- The registrar's expiry emails.
- Members writing in.

**Immediate response**
1. At the registrar: renew or unlock, and check the nameservers.
2. `getniyyah.netlify.app` keeps serving the same deploy the whole time. Tell members in the channel to use it.

**Recovery**
- Recover the domain.
- If it is gone for good: point a new domain at Netlify, set `VITE_SITE_HOST`, and redeploy. Every link the app mints then carries the new host. The domain drill checks that nothing else hard-codes the old one.

**Data-loss bound**
- None on the server.
- **On phones, access is lost, not data**: `localStorage` belongs to the origin. On a new address, a member sees an empty app until she restores with her code. Anyone who never kept a map cannot carry her answers across.

**User impact**
- Every link already sent is dead: restore links, the eleven, vouch links and tool links.
- The printed sheets carry `joinniyyah.com` on paper by design and cannot be recalled.
- `salaam@joinniyyah.com` mail stops.

**Prevention: the founder's, and the most important in this document** (`docs/CONTROL.md` rank 1):
- auto-renew on;
- the registrar lock on;
- a multi-year renewal;
- the registrar row in `docs/CONTROL.md` filled in.

The domain drill: built with `VITE_SITE_HOST=getniyyah.netlify.app`, only the sheets and the contact address still name `joinniyyah.com` (drill log).

### 9. Guide runaway cost

**Detection**
- `cost` red at `OPS_COST_ALERT_USD`, amber at 3× the week.
- `limits` red when the guide's daily cap is reached.
- The Anthropic console.

**Immediate response**
- Lower `GUIDE_DAILY_CAP` in Netlify. It takes effect on the next call, with no redeploy.
- If the key itself is abused, follow scenario 4.

**Recovery:** raise the cap back once the cause is known. Real launch traffic is a reason to raise it.

**Data-loss bound:** none. Money is bounded by the daily cap: about $36 on the worst possible day, and less with a lower cap.

**User impact:** past the cap, the guide answers offline until midnight UTC.

**Prevention:** already built and drilled (`tests/ops.test.ts`): the caps fail closed, the body and history are bounded, and there is the cost alarm. Outside the code: the console's spend limit (unset).

### 10. Founder laptop loss

**Detection:** the founder knows.

**Immediate response, the same day, from another device:**
1. **GitHub:** Settings → Sessions → sign out everywhere, and revoke personal access tokens.
2. **Netlify:** revoke personal access tokens (User settings → Applications), and sign out other sessions.
3. **Rotate `FOUNDER_KEY`** in Netlify and GitHub in the same hour, and **rotate `ANTHROPIC_API_KEY`** (scenario 4). Both may have been in a local `.env`.
4. **The mailbox** behind `VITE_CONTACT_EMAIL`: sign out other sessions.
5. **The registrar:** change the password.
6. The contacts backup (`reach-<date>`) and any `backup-*.json` on the laptop now sit with whoever has the laptop. The disk should have been encrypted; if it was not, treat those files as disclosed and follow `docs/PRIVACY.md`.

**Recovery:** sign in from a new device with 2FA and recovery codes. Clone the repository; nothing needed to run the product lives only on the laptop.

**Data-loss bound**
- None of the product's data: it lives in Netlify and GitHub.
- The saved backups and contacts on the laptop are lost *and* possibly exposed.

**User impact:** none, if the rotation is done the same day.

**Prevention: the founder's**
- 2FA on every account in the `docs/CONTROL.md` table.
- Recovery codes stored off the laptop.
- The filled accounts table sealed with one trusted person, as `docs/CONTROL.md` asks.
- Full-disk encryption.
- Backups kept somewhere that is not the laptop.

This is also a tabletop drill, run twice a year (below).

## Tested, or only written down

| Procedure | How it is held |
|---|---|
| Restore from backup | **Every PR**: a round trip, a dry run that writes nothing, never over newer data, refuses what is not a backup. **Quarterly**: the founder runs `scripts/restore.ts` against a **scratch Netlify site** (never production) with the last real backup. |
| Corruption tolerance | **Every PR**: garbage planted in every store; no route crashes; the backup arrives and says what it skipped. |
| Migrations | **Every PR**: the golden corpus (`v0`, `v1`) through every reader. |
| Maps recovered from phones | **Every PR**: `maps` wiped; keep, door join and vouch ask each recover. |
| Detecting mass deletion | **Every PR**: a wipe turns `data` red; a lost safety queue turns it red. |
| Lost or rotated secrets | **Every PR**: each secret unset fails closed or offline; a rotated founder key refuses the old one everywhere. **Quarterly**: the real rotation (`docs/CONTROL.md`) *is* the drill. |
| Netlify outage | **Every PR**: the rendered app with the server down from the first tap. The response is communication only, and is written down. |
| Guide runaway | **Every PR**: `tests/ops.test.ts`. |
| Rollback | **Once, then after any change to Netlify's interface**: in a quiet hour, publish the previous deploy, confirm the site and `deployed.yml`'s smoke test, then publish the latest again. The button moves; the minutes matter. |
| Domain failure | **Every PR**: the guide pages carry the configured host. **Written down**: the registrar steps, which cannot be drilled safely. |
| Laptop loss | **A tabletop drill twice a year**: from a clean browser, sign in to GitHub, Netlify, Anthropic, the registrar and the mailbox using 2FA and recovery codes alone, then rotate `FOUNDER_KEY`. If any sign-in fails, that is the finding. |

**Why the split falls where it does:**
- **Tested:** everything that *code* does on the worst day. It breaks silently, and only on old or broken data, which no one sees until they need it.
- **Drilled by hand:** everything that depends on a vendor's interface or on an account. No test can reach those, and they change without notice.
- **Written down only:** what cannot be simulated without doing it for real (losing the domain), where the prevention is the whole of the answer.

## What is the founder's alone

These are the five settings no code can reach, each of which closes a scenario above:
1. the Anthropic console's **monthly spend limit** (scenarios 4 and 9);
2. the registrar's **auto-renew and lock**, and its row in `docs/CONTROL.md` (scenario 8);
3. **2FA and recovery codes** on every account, sealed with one trusted person (scenario 10);
4. the **repository made private**, then `BACKUP_TO_ARTIFACT=true`, so the monthly backup takes itself (scenario 6);
5. the three drills marked *not yet run*.
